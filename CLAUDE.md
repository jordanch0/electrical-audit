## CLAUDE.md · Project Intelligence File

## What This App Is

SparkCheck is a **Progressive Web App (PWA)** for electrical auditors and site electricians. It runs entirely in the browser with no backend — all data is stored in `localStorage`. It is deployed as a static site via **GitHub Actions → GitHub Pages** and can be installed on iOS/Android as a standalone app.

The app is built with **React + JSX**, bundled by **Vite**. Source lives in `src/App.jsx` (one very large file, over 17,000 lines: find a function by its name, never by a line number). The entry point is `index.html` → `src/main.jsx` → `src/App.jsx`.

**Version:** v11 (shown in AppRoot footer)
**Brand colour:** `#e8731a` (SparkCheck orange)
**Light theme throughout:** background `#e8e6e2`, surface `#f7f6f3` (the earlier dark `#111`/`#161616` theme is gone)

### Build Pipeline
- **Dev server:** `npm run dev` — Vite HMR at `http://localhost:5173`
- **Production build:** `npm run build` — outputs to `dist/`
- **Deploy:** Push to `main` → GitHub Actions runs build → deploys `dist/` to GitHub Pages automatically
- **No manual file editing of dist/** — always edit `src/App.jsx`, then build

### XLSX Library
The `xlsx` (SheetJS) package is imported as:
```js
import * as XLSX_LIB from 'xlsx';
const XLSX = XLSX_LIB; // module-level alias — all bare XLSX. calls resolve here
```
Do not change this pattern. There are known security vulnerabilities in the xlsx package — do **not** run `npm audit fix --force` as it will break things.

### State & Storage
- All data lives in `localStorage` under versioned keys (e.g. `rcd-projects-v6`, `rcd-results-v6`)
- Each module has its own storage keys to avoid collisions
- Async `load(key, fallback)` and `save(key, val)` helpers wrap localStorage with error handling
- Storage-full warning banner shown to user if save fails
- Photos and logos live in four IndexedDB stores (`sparkcheck-site-photos`, `sparkcheck-gsd-photos`, `sparkcheck-app-settings`, `sparkcheck-site-logos`). Backup, restore and Delete all data cover both localStorage and these stores: see "Backup, restore and Delete all data" under Design System.

**Bottom bars: layout history, and the Facebook-style overlay restyle (2026-09-29 -> 2026-09-30)**:
1. **Non-scrolling reserved layout (kept from the 2026-09-30 re-fix)**: the scrollable module grid and the Home-screen bottom bar are SEPARATE flex children of the home screen's outer column — the grid in a `flex:1, overflowY:"scroll"` region, the bar in a non-scrolling row below it. **This replaced an earlier `position:fixed` pill design** that floated two pills OVER the scrollable grid: whatever content happened to be scrolled to that fixed screen position — including the last module card — could end up directly behind them (a first-attempt trailing spacer only protected the one scroll position where it lined up with the still-floating pills, and was confirmed still broken). **Date maths rule (app-wide):** ISO `YYYY-MM-DD` strings parse as UTC midnight, so month/year additions must use `setUTCMonth`/`setUTCFullYear` (`addMonthsISO`, `addYearsISO`, `addTATMonths`). Local `setMonth` + `toISOString()` lost a day across daylight saving (13/07 + 3 months gave 12/10 in Sydney). `swbAddYear`/`irtAddYear` are `backupDmy(addYearsISO(d, 1))` (UTC maths and a string formatter, release t): the same day in every time zone, covered in Sydney, UTC, Los Angeles and Auckland by `src/date-helpers-dst.test.js`. **Known limit: `fmtDate` formats in local time (`new Date(d).toLocaleDateString`), so a stored ISO date shows a day early west of UTC (96 call sites; the app's users are in Australia), a candidate for its own release. Never fix a date helper with `fmtDate(addYearsISO(...))`: it is wrong in Los Angeles (a test pins that).**

## Coding Conventions

- **React.createElement** — all components use `React.createElement(...)` (no JSX syntax in source — Vite handles the transform but the code pre-dates JSX migration and was not converted)
- **Single file** — all components remain in `src/App.jsx`; do not split into separate files unless explicitly asked
- **Functional components only** — React hooks (`useState`, `useEffect`, `useCallback`, `useRef`, `useMemo`)
- **Inline styles everywhere** — no CSS classes, no stylesheets. All styling via `style={{...}}` objects
- **Light theme constants**: bg `#e8e6e2`, surface `#f7f6f3`, border `#e4e4e7`, text `#18181b`, muted `#52525b`
- **Bottom nav (floating pill, 2026-10-01)**: every module AND the Home screen use ONE floating pill, `NAV_PILL_STYLE` (`NAV_PILL_STYLE_NARROW` on Home: 2 tabs, max 240px, centred) — `position:absolute` over the content, 14px from each side, `borderRadius:999`, translucent white + blur, `0 4px 16px rgba(0,0,0,0.12)` shadow. **Size/position (re-measured against Facebook's bar, 2026-10-01): pill 52px tall (`NAV_PILL_H`: 44px buttons + 3px padding + 1px border); bottom offset `NAV_BOTTOM = max(8px, env(safe-area-inset-bottom) - 14px)` = 20px on a home-indicator iPhone (the pill DIPS into the safe area like Facebook's), 8px where there is no inset; `NAV_CLEARANCE = NAV_PILL_H + NAV_BOTTOM + 16px` (= 88px on such an iPhone).** `NAV_BOTTOM` is the single bottom number — the pill and `NAV_CLEARANCE` both use it; never hard-code a bottom offset. It relies on `viewport-fit=cover` in index.html's viewport meta (without it the inset is 0 and the pill can't dip). ONE button, `NavBtn` (`IELNavBtn`/`TATNavBtn`/`SWBNavBtn`/`ThermoNavBtn`/`IRTNavBtn` are aliases — never write another): the active tab is a `#fdeadb` rounded highlight with `#a3530f` icon + label, inactive `#3f3f46`, 11px labels, `NAV_BTN_H` 44px (tap target never lower). Every module's `bottomNav` is just `NAV_PILL_STYLE`.
- **SCROLLABLE SCREENS MUST USE `NAV_CLEARANCE` FOR BOTTOM PADDING — never a hard-coded number.** The pill floats OVER the scroll area, so any scroll container on a screen that shows the pill must end with `paddingBottom: NAV_CLEARANCE` (pill height + gap + safe-area inset + breathing room). This is what the 2026-09-29/30 overlay attempts got wrong twice (last card hidden behind the bar). The module `main` regions and the Home grid carry it; views rendered INSIDE `main` must not add their own (it would double up). New scroll area = use `NAV_CLEARANCE`. A message that EXPANDS inside such a scroll area must also scroll itself clear of the pill, with `scroll-margin-bottom: NAV_CLEARANCE`; Global Settings does (`useGsReveal`) and so do the modules' confirm cards (`useRevealOnOpen`, release q). **RULE: a confirm card that can grow (anything that calls `useCollapsible` and opens in place) must call `useRevealOnOpen(boxRef, open)` before any early return and spread `...GS_MSG_MARGIN` on the card; `src/reveal-scan.test.jsx` fails for a new one that does neither and is not on its allow-list with a reason.** The hook runs only when `open` turns true (two animation frames, then the same 12 px / 16 px-above-the-pill band as Global Settings, `nearest` unless taller than the room, `auto` under reduced motion); it finds the scroller (the nearest `[data-gs-scroll]`, else the nearest ancestor with `overflow-y` auto / scroll) and the pill (the `<nav>` that is a direct child of the scroller's parent; none on a sites list) itself. On the card list: `ConfirmReset`, `CompleteAuditBtn`, `ContinueConfirmBtn` (and its Thermo / Switchboard wrappers), `DropdownNotice` (also the Switchboard / ELT / Welder / GSD view) and the Calendar `EventCard` delete. Left out on purpose: `DeleteButton` (GSD keeps its own `revealBottom`, pinned by `gsd.test.jsx`), the `StyledSelect` / editable-dropdown popovers (a list that opens below its field: a later release), `AuditorRequiredNote`, import error lines, forms, banners and alerts. Tests: `src/reveal-on-open.test.jsx` (the hook), `reveal-cards.test.jsx` (the shared components and the Calendar), `reveal-modules.test.jsx` (the nine modules through the real screens), `reveal-scan.test.jsx` (the source scan). `src/safe-area-layout.test.jsx` scans the source and fails on a `main` region without it or a `paddingBottom: 80/100` literal. Global Settings' scroll column is one too (it also shows the pill, as a `<nav>` inside its own `position:relative` screen).
- **iOS standalone short web view — why the pill once sat ~47pt too high (2026-10-01). Cause: `html, body { height: 100% }` alone.** On a real iPhone (installed, portrait) `window.innerHeight` was 879 on a 926pt screen: `100%` resolved 47pt short (the status-bar inset) and the WEB VIEW followed it — nothing below 879 is ever painted, so `#root`'s `bottom:0` and the pill (correctly 20px above it) sat 67pt above the real bottom with a blank strip underneath. Nothing in the app added the inset twice, the browser / iframe can't show it (inset 0), and sizing `#root` taller with JS does NOT work (the pill's lower half is clipped at 879). Found with a live-experiment panel on the phone: only `html/body height:100vh` moved `innerHeight` 879 -> 926 (re-adding the viewport meta, `overflow:visible`, `scrollTo`, `body:fixed` did nothing). **Fix: `index.html` declares `height:100%` and then `height:100vh` on `html, body`** (`100vh` = 926 there). Rules: never remove that `100vh` line; never "fix" iOS viewport height with JS reading `screen.height` / `innerHeight`; and judge pill / bottom-edge positions on a real device (a desktop browser's inset is 0). Tests: `src/safe-area-layout.test.jsx` (the 100%-then-100vh order, and no `screen.height` hack).
- **The pill must NEVER depend on `--kb-inset`, and it HIDES while the keyboard is open (2026-10-01).** `--kb-inset` (a margin-bottom on the nav) lifted the pill with the iOS keyboard and was left stale when a nav tap closed the keyboard without a final viewport event (pill stranded mid-screen). It is gone — nothing in `index.html` or `src/` sets or reads it. Instead `index.html`'s inline script derives `html.kb-open` from `document.activeElement` (a text input / textarea / select / contenteditable) on focusin / focusout / blur / visualViewport resize+scroll / pagehide, and `html.kb-open #root nav` is `opacity:0; pointer-events:none` (0.15s fade). A nav-button press blurs the field first. Never position anything off the keyboard height; it can't be read reliably on iOS.

- **Australian locale**: dates DD/MM/YYYY, currency $AUD implied, standards references to AS/NZS

## Design System / Interaction Standards

### Standard Delete Pattern — applies to ALL modules, ALL destructive actions

All destructive actions use a **two-step inline confirmation** via the shared `DeleteButton` component.
**Never use `window.confirm()`, modals, browser dialogs, or any other confirmation pattern.**

#### Component signature
Defined once in `App.jsx` — after the shared utility functions, before the first module function.

```js
// Module-level variable — ensures only one DeleteButton is in confirm state at a time
let activeDeleteSetter = null;

function DeleteButton({ onDelete, label = 'Delete?' }) {
  const [confirming, setConfirming] = React.useState(false);

  const open = () => {
    if (activeDeleteSetter && activeDeleteSetter !== setConfirming) {
      activeDeleteSetter(false); // close any other open instance
    }
    activeDeleteSetter = setConfirming;
    setConfirming(true);
  };

  const cancel = () => {
    activeDeleteSetter = null;
    setConfirming(false);
  };

  const confirm = () => {
    activeDeleteSetter = null;
    setConfirming(false);
    onDelete();
  };

  if (!confirming) {
    return React.createElement('button', {
      onClick: open,
      style: {
        border: '1px solid rgba(239,68,68,0.35)',
        color: 'rgba(239,68,68,0.7)',
        background: 'transparent',
        borderRadius: '6px',
        padding: '4px 8px',
        cursor: 'pointer',
        fontSize: '13px',
        lineHeight: 1,
      }
    }, '🗑');
  }

  return React.createElement('div', {
    style: { display: 'flex', alignItems: 'center', gap: '8px' }
  },
    React.createElement('span', {
      style: { color: '#f87171', fontSize: '13px' }
    }, label),
    React.createElement('button', {
      onClick: confirm,
      style: {
        background: 'rgba(239,68,68,0.12)',
        border: '1px solid rgba(239,68,68,0.5)',
        color: '#f87171',
        borderRadius: '999px',
        padding: '4px 14px',
        fontSize: '13px',
        cursor: 'pointer',
        display: 'flex',
        alignItems: 'center',
        gap: '6px',
      }
    }, '🗑 Delete'),
    React.createElement('button', {
      onClick: cancel,
      style: {
        background: 'rgba(255,255,255,0.06)',
        border: '1px solid rgba(255,255,255,0.12)',
        color: '#aaa',
        borderRadius: '999px',
        padding: '4px 14px',
        fontSize: '13px',
        cursor: 'pointer',
      }
    }, 'Keep')
  );
}
```

#### Usage
```js
// Inside a map() — always close over the item id
React.createElement(DeleteButton, { onDelete: () => deleteItem(item.id) })

// Custom label
React.createElement(DeleteButton, { onDelete: () => removeArea(area.id), label: 'Remove area?' })
```

#### Behaviour rules
- **Idle state:** small 🗑 trash icon button, right-aligned, low emphasis, subtle red border
- **Confirming state:** same row expands to show `Delete?  [🗑 Delete]  [Keep]`
- **Keep:** returns to idle, no action taken
- **Delete:** calls `onDelete()` immediately, no further prompt
- **Only one open at a time, and a click OUTSIDE collapses it** — both come from the shared `useCollapsible(open, close, ref)` hook (module-level `activeExpander`; a document-level `click` listener in the CAPTURE phase, deliberately not `pointerdown`, so a layout shift can never lose a tap). It is used by `DeleteButton`, `ConfirmReset`, `CompleteAuditBtn`, the Calendar event card's delete, the popover of all five editable dropdowns and GSD's area picker; anything new that expands must use it, and a confirm card that can grow must also call `useRevealOnOpen` (release q). Deliberately NOT collapsible: inline add / edit forms (they hold typed input) and accordions (navigation). This replaced the old `activeDeleteSetter`. Tests: `src/collapsible.test.jsx`
- **No layout shift** — row/card dimensions must not jump between idle and confirming states
- **No modals, no `window.confirm()`** — confirmation always happens inline in the row

#### What to remove when replacing old patterns
Remove all of the following when converting a delete action to `DeleteButton`:
- Any `window.confirm(...)` call
- Any home-grown confirm state variables: `deleteConfirm`, `confirmDelete`, `confirmId`, `showConfirm`, `pendingDelete`, `deletingId`, `deleteId` or similar
- Any inline ternary "Are you sure?" / confirmation UI rows
- Any modal or dialog that exists solely to confirm a delete

### The date model (2026-10) — device-local dates, the Home date follows the day, per-item dates

**1. "Today" is always the device's own local date.** Use `localISODate(d = new Date())` (local getters, `YYYY-MM-DD`) and `isoFromDateText` (the one parser for typed / imported dates). **Never** `new Date().toISOString().slice(0, 10)` for "today", and never a named time zone in `src` (the app runs on phones in whatever zone they are in; a hard-coded zone is wrong the moment the device travels). The old code used the UTC date: in Sydney (UTC+10 / +11) it said "yesterday" until mid-morning, in the Americas it said "tomorrow" every evening, so Home dates, stamped dates and due flags were off by a day for hours at a time. Month / year arithmetic stays UTC-safe (`addMonthsISO`, `addYearsISO`: see the Date maths rule). Tests prove the zones by running the REAL helper source (cut from `src/App.jsx` between `// <name>` markers) in child node processes with `TZ=<zone>` (`src/local-date.test.jsx`): vitest workers cannot change the zone. CI runs the suite with `TZ: Australia/Sydney`.

**2. The Home date follows the day.** Every module's Home "test date" (RCD: push date and injection date) is set automatically to the device's local date, and a stored meta record carries `dateDay` = the local day it was last set automatically. `useHomeDateFollow(mod, loaded, setAllMeta, projects)` (called in every module after its state hooks) checks on app open, on return to the foreground (`visibilitychange` / `focus` / `pageshow`) and from a timer armed for the next local midnight (`msToLocalMidnight`, re-armed at every check from the device's clock). For a site whose `dateDay` is not today: the Home date becomes today and `dateDay` = today. A **manual edit** of the Home date only changes the date (and stamps `dateDay` via `setMeta`), so it **holds until the next day change**. A stored next-due that is only the **default** for the old date (empty, or old date + the module's interval) **moves with it; a chosen one stays**. The intervals are the single table `HOME_DATE_SPECS` (RCD push +1 month / inject +1 year, IEL +3 months, ELT +6 months, Welder +3 months, Thermo / SWB / IRT / GSD +1 year; TAT has no Home next-due). The follow only updates meta records that already exist for existing sites (never creates one, never touches an orphan) and touches nothing else: not results, History, the active flag or the gate. **Reset and Complete Audit start a new audit, so they set the Home date back to today's local date and `dateDay` to today (`homeDateRelease`, all nine modules; RCD both the push and the injection date): a hand-edited (backdated) date is released and never inherited by the next audit. A default next-due moves with it, a chosen one is still cleared by Reset (Complete leaves it as before); a day change after that works as before.** It also waits until the module's item-date migration has run cleanly (`ITEM_DATES_READY`), so an old Home date is read before the follow moves it.

**3. Item dates, all nine modules.** Every tested item carries its own date in `lastTested` (RCD: on each push / inject record; IEL / TAT: the item; SWB: the checklist point; IRT: the item; Thermo: each logged test entry; ELT / Welder: the fitting / welder record; GSD: the defect, labelled **DATE LOGGED**). Rules, applied in each module's ONE patch function through `itemDateApply(next, hasResult, home)` (RCD `patchCircuit` and the panel "all" buttons, IEL / TAT / SWB `patchItem`, IRT `patchItem`, ELT / Welder `patchAsset`, GSD `patchItem` plus create / duplicate): the date is **stamped from the Home date at the FIRST result only**; **a changed result keeps the date** (PASS -> FAIL -> N/A never restamps); **"—" (or clearing every answer) clears it**; **Reset and Complete clear it** (they clear the results; Complete's History snapshot keeps its own dates); a hand-edited date holds, and clearing it by hand restamps the Home date. IRT sends its whole form (it holds no date of its own), so its `patchItem` keeps the stored date unless the date itself was edited. A "result" is `itemHasStatus` (status other than untested), IRT `irtHasResult` (a status, or readings = auto-detected), ELT `eltHasResult` (any of the 4 checks), Welder `welderHasResult` (any answered item); a GSD defect always has one. **Switchboard is the exception: its item (checklist point) page shows NO date and NO NEXT TEST DUE (release l); the one date is the BOARD date on the board page. The item's `lastTested` is still stamped at the first result and kept in storage (it feeds the board-date backfill), but it is not shown or editable anywhere.** **Every other module's item page shows `ItemDateField` (DATE TESTED; GSD: DATE LOGGED) only once there is a result**, always the shared `DateBox`. **NEXT TEST DUE** (`ItemDueBanner`, directly under the date; GSD has none) is **read-only** and shown for **PASS and FAIL only** (never N/A, which is not a test; ELT / Welder: once the fitting / welder is PASS or FAIL overall; Thermo: every logged entry is a test): `itemNextDue` = the item date + the module's interval (the `HOME_DATE_SPECS` intervals), **or the Home next-due when the auditor chose one** (it differs from Home date + interval). It means "if this is the test date, the next test is due on this date". **SWB also has a board-level date** (the board page's DATE TESTED / NEXT TEST DUE, directly under Add Photo): the scalar `_lastTested` on the board record, next to `_photos` and the per-test keys. Stamped from the Home date at the first result in the board, kept when a result changes, cleared when no test on the board has a result (and by Reset board, Reset and Complete); a hand edit holds and clearing it by hand re-stamps the Home date; shown only once a test on the board has a result; NEXT TEST DUE for PASS / FAIL only (+1 year or the chosen Home date). The stored per-test dates are not shown (see above): editing the board date never rewrites them and a later result never rewrites the board date. A board whose first result was an N/A on an earlier day keeps that earlier day as its board date even when the first PASS or FAIL comes later (intentional).

**4. Export header rule.** Date Tested (header row 4) = the **earliest PASS or FAIL item date** (N/A does not count; Thermo counts MONITOR; GSD uses the earliest DATE LOGGED); Next Test Due = the **earliest item next-due** (TAT: PASSED items only). With no qualifying item the header falls back to the Home values. Per-row Date / Next Test Due columns come from the item; **a blank item date stays blank in an export — never the Home date**. Helpers: `earliestIso`, `itemDue`, `itemNextDue`. SWB: a board's Register Date Tested / Next Audit Due and the header come from the BOARD date (header: earliest board date among boards with a PASS or FAIL; N/A-only boards do not count), blank stays blank; the board sheets have NO per-test "Date Tested" column (seven columns, A-G; release l): a board's own date is in its Register row and in its sheet's Asset Details block; the GSD Register has a "Date Logged" column.

**5. The migration (old results get a FIXED date).** Results saved before item dates existed are backfilled at load by `itemDatesMigrate` / `itemDatesLoadStep`: a live site's items get that site's STORED Home date (the local day only for a site with no meta), a History snapshot's items get the snapshot's OWN date, never the live Home date (which now changes daily). It is **data-driven**: a meta record (or a snapshot's meta) **without `dateDay` is old-format data**, so a backup made before this release and restored afterwards is covered too (no marker key). It runs **in memory** inside each module's load; the module's normal save effects persist it (the same path as the audit-active migration, with the storage-full safety net; nothing here touches storage itself). On an error the data is returned untouched and the module is not marked ready (the follow stays off, the next load retries). It is additive (only items with a result and no date) and idempotent, and it runs **before** the Home-date follow. **Known gap:** a partial restore of results only, over a current meta, is not covered. SWB boards also get a board date at load (`swbBoardDatesBackfill`): a board with results and no board date gets the EARLIEST per-test date on it (never the live Home date; blank stays blank). Not gated on `dateDay` (boards stamped by an earlier release need it); idempotent.

**6. No OVERDUE / DUE SOON flags (IEL had them; removed 2026-10).** Next Test Due is informational and appears in the exports. Reset and Complete clear results and dates, so a flag could only fire on an item tested earlier in an audit that is still open, a hand-edited past date, or a past Home due date: a warning that is almost never true is noise. `isOverdue` / `isDueSoon` are gone; do not reintroduce them. (The Calendar's own "OVERDUE Nd" display is separate: it is about scheduled calendar events, `daysUntil`.)

**7. Every date input is a `DateBox`.** A raw native `<input type="date">` ignores width on iOS Safari and overflows its container, so a date field on a form page is the shared `DateBox` (a styled box showing DD/MM/YYYY over a transparent native date input that catches the tap; `ItemDateField` wraps it). The Home pages use the same overlay pattern inline. Never add a bare `type="date"` input.

**8. Test seeds.** `src/test/setup.js` wraps `Storage.prototype.setItem`: a NEW `*-meta-v<n>` record written WITHOUT a `dateDay` is stamped "already followed today", so a test that seeds a fixed past Home date is not moved by the follow (a record that already exists keeps what it had; records the app writes already carry `dateDay`). Tests of the follow / migration themselves seed OLD-format data with **`rawSetItem(key, value)`** (a global from `setup.js`: the unwrapped `setItem`). There is no `rawClear`: `localStorage.clear()` needs no escape hatch (the migration has no marker key). Faked-clock tests fake **only `Date`** (`vi.useFakeTimers({ toFake: ['Date'] })`). Shared UI helpers for the item-date tests: `src/test/item-dates-ui.js` (Home date 5 Oct, device day 7 Oct, `dateDay` = today). Tests: `item-dates-migration`, `home-date-follow`, `item-dates-iel-tat`, `item-dates-<module>.test.jsx`, `local-date`.

### Backup, restore and Delete all data (2026-10; Global Settings → Backup & Data section)

Global Settings has two sections, **Business | Backup & Data** (labels in the one constant `GS_TAB_LABELS`; the ids stay `company` / `data`), shown as the Calendar's floating bottom pill: a `<nav>` styled `NAV_PILL_STYLE`, buttons `NAV_BTN_STYLE`, absolute inside the screen (which is `position:relative; overflow:hidden`), with the same position, offsets, safe-area bottom and z-index as every module's bar (`role="tab"`; both panes stay mounted; the sections hold still while a restore, undo, backup build, build self-check or file check runs and in settings-only mode; Left / Right keys; it opens on Backup & Data when a restore problem is recorded, for `initialTab="data"` and in settings-only mode). A locked section shows a lock, Backup & Data shows a warning triangle while a restore problem is recorded, and the active section is marked by the highlight, bold text and `aria-selected` (never colour alone). The Backup & Data section is: the Storage gauge, Backup and restore, then Delete all data. **What keeps content clear of the pill is the shared rule, not a gap and a line:** the scrolling column ends with `NAV_CLEARANCE` (the same padding every module's scroll area has), so the last item (Save on Business; Delete all data and its question on Backup & Data) always stops 16 px above the pill; and the pill is a `<nav>`, so `index.html` hides it while a text field has the keyboard (`html.kb-open #root nav`). Never give this screen its own tab look or a hard-coded bottom padding (`src/backup-tabs.test.jsx` and `src/backup-nav-pill.test.jsx` pin it, the latter against the Calendar's own bar). The earlier rule "the tab bar keeps a 10 px gap and a 1 px line under it" is gone: it belonged to the old top bar. A message that opens in the section is scrolled into view when it is hidden (see "Messages that open are scrolled into view" below); the scrolling column carries `data-gs-scroll` so the helper can find it.

- **The backup file** is one plain `.zip`, `SparkCheck-backup-YYYY-MM-DD.zip`: `manifest.json` (format `sparkcheck-backup`, formatVersion 1, appVersion = the build id, per-entry size + SHA-256), `data.json` (`{ localStorageKey: rawJsonText }` for every key the app owns) and `files/<store>/<n>.bin` (one entry per IndexedDB record: photos, thumbnails, logos). Entries are written and read ONE AT A TIME, so memory is bounded by the largest record, not the archive. Photos are optional; logos and data always go in. It contains client names, the ABN and photos: the footnote under Make backup says so and to store it somewhere safe.
- **Delivery (never reorder):** measure (`backupMeasure`) → a warning at 100 MB or more (`BACKUP_LARGE_BYTES`; it offers "without photos") → build (slow) → the built file is run through the SAME check a restore runs (`backupInspect`, inside `build` in `BackupRestoreSection`) and is NOT offered if it fails ("The backup could not be used", no Share, no "Last backup"; the reason goes to the log only) → a SECOND tap, Share backup (`backupDeliver`). `navigator.share` only opens inside a tap, so build and share are separate taps; where there is no share sheet the file is downloaded. "Last backup" (`sparkcheck-last-backup-v1`) is recorded only when the file was really handed over (a closed share sheet records nothing). It is shown as the day and the device's local time: `today, 4:38 pm`, `yesterday, 4:38 pm`, `13/10/2026, 4:38 pm` (12-hour clock, lowercase am / pm, written by hand in `backupTimeText`, never `Intl`); the time comes from the record's `at`, and a record whose `at` cannot be used (or is not on its own `day`) shows the day only; reading the record never writes it. The Delete all data question quotes the same text.
- **Restore ADDS and FILLS; it never replaces or removes (release n); a site that differs is added as a COPY (release o).** A calendar event or History snapshot whose ID is already on the phone is skipped. A SITE whose ID is already on the phone is compared with the backup's version (next bullet): identical content is skipped, different content is added as a separate copy; nothing you have set on the phone is modified or deleted. A photo, thumbnail or site logo that already exists is never overwritten: identical bytes are reused for a site that is added as itself, different bytes make that WHOLE site "not restored: conflicting photos" (a COPY never reuses or conflicts: its photos and logo are new records). **FILL WHOLE SETS, ONLY WHERE THE WHOLE SET IS EMPTY (`backupPlanSettings`, `backupSettingsInserts`, `backupBizFill`, `backupKeyFill`, `backupKeyIsEmpty`, `BACKUP_LIST_SPECS`).** There are NO MIXED SETS. The file holds the Business tab record (`app-settings-v1`: name, ABN, licence), the company logo (`files/app-logo/`), every module's dropdown lists and the Test & Tag lists. **The business details are ONE set** (business name, ABN, licence and the company logo): filled from the backup only when ALL FOUR are empty on this phone (blank or spaces only is empty; the logo counts as there when the phone has a logo record; a backup whose Business tab has no logo flag brings no logo); if any one of the four is set, none is touched. **A module's lists and settings are ONE set** (Test & Tag: its dropdowns, equipment types, frequencies, appliance names and default settings together): filled only when every list key of the module is absent or exactly the built-in default (an Emergency Lighting / GSD list at its old default counts as the default; an emptied list, an extra entry, a different order or a field the app does not know all mean the phone's own); then each key the backup holds with its own values is written whole (the module's defaults stay where the backup brought none). If any list of the module differs, the whole module is left alone. The step that builds the writes refuses (nothing is written) if a set stopped being empty between the plan and the writes. **Undo takes a set out only if it still holds exactly what the restore wrote** (every key of the module, also the ones the restore left as they were; for the business set the three texts, the flag and the logo bytes); if the person changed it since, that whole set is left alone and the result card says so. **Never restored:** `rcd-mode` and `iel-cat` (old keys the app no longer writes: a restored one would be read by the one-time audit migration and turn every site into a mid-audit one), the photo-migration markers, the app's own notes, and a list key of another version. A set with anything of your own in it (one business field, an entry added or removed, a different order, an emptied list) is never touched, not even its empty parts. It brings back sites with their results, meta, History and audit-in-progress flags, calendar events, photos with thumbnails, per-site logos, and those fills. Tests: `backup-fill.test.jsx` (every edge, the empty phone, own values, rollback at every write, Undo, old files) and `backup-fill-screens.test.jsx` (all nine modules' Dropdowns tabs and the Business tab).
- **Copies of changed sites (release o; `backupClassifyExisting`, `backupPlanCopies`, `backupBuildIdMap`, `backupRemapIds`, `backupVerifyCopies`).** Same ID and identical content: nothing to add. Same ID and different content: the backup's version is added as a NEW site with a new ID, named `<name> (backup 12 Oct 2026)` (the backup's day written as day, short month name and year, `backupDayText`: no slash, so the name is safe inside a file name; ` 2`, ` 3` when that name is already used in the module). **Same content** = the site record, its results, its meta, its History snapshots and the bytes of its photos, thumbnails and site logo. **Ignored** (the Home-date follow rewrites them every day): the meta's `dateDay`, the test date(s) and their default next-due date(s) (`backupMetaStable`, from `HOME_DATE_SPECS`); data saved before item dates existed is brought to the stored form first (`backupNormalise`); photos are left out of the comparison when the backup was made without them. **ONE id map** per restore (`backupBuildIdMap`: site id, History snapshot ids, photo ids; each new id is checked against the phone's ids, the backup's own and the ids already given out) and **ONE re-pointing function** (`backupRemapIds`) for every module. It replaces ids only where the app keeps them (the project id; a snapshot's id and `projectId`; the photo pointers, found with the app's own extractors in `BACKUP_PHOTO_ARRAYS`) and a copy REFUSES itself ("could not be copied safely") when an old id is left anywhere else. Each copy gets its OWN photo, thumbnail and site-logo records (written with `add`, never over anything); the site on the phone is never written to. Calendar events are not copied or re-pointed: they name a site as text. After the writes `backupVerifyCopies` checks that every copy exists once with the right name, holds exactly its own History and photos, points at nothing of the site it was copied from, holds as many records as the backup's site and, with the ids mapped back, equals it record for record, and that every photo and logo is the backup's for that site (bytes); any mismatch rolls the whole restore back with the existing journal. In a whole restore the byte check before it (`backupVerifyApplied`) stops a tampered key first, so `src/backup-copies-rules.test.jsx` ("the after-write check on its own names each fault") calls `backupVerifyCopies` directly on a finished restore: each of its checks has its own message and its own test. **Repeat restores:** the note `sparkcheck-copies-v1` (`{ "<module>:<newId>": { from, digest, backupDate, name } }`; never in a backup, removed by Delete all data) remembers which backup version is already on the phone as a copy, so the same version is never copied twice (even if the copy was renamed); a copy the person deleted is added again. **Undo** removes the copies with their History, photos, logo and notes, except a copy the person has changed since (it must still equal what the restore wrote, `undo.copies[module][id].digest`): that one is kept and counted. **Together with the release n progress and Undo wording:** the restore progress counts the photos of copies too (a copy's photos are photos: the last "photos N of M" value is the sum of the photo numbers the summary shows, the added sites' and each copy's); the Undo question, the "Restore undone" card and the "Last restore:" line under Undo name copies in their list as "site copies" ("1 site, 2 site copies and 3 History snapshots"; plain sites are `sites - copies`, `backupCountParts` / `backupCountWords`, `backupUndoResultText`, `backupLastRestoreLine` uses the same parts and adds the photos last; the engine returns `copiesRemoved`), leave out any zero ("Last restore: 1 site, 2 site copies, 3 History snapshots and 9 photos added on 19/10/2026. Undo is available until 02/11/2026."; a restore with no copies reads as it always did), the Undo question says "A copy you have changed since is kept, with your changes.", and the card says "1 copy you changed since was kept." / "2 copies you changed since were kept."; Delete all data removes the copies note with every other owned key (it is on `backupKeyExcluded`). Tests: `backup-copies.test.jsx` (every module: copies, bytes by site, Undo, repeats), `backup-copies-rules.test.jsx` (same / different, rollback, id clashes), `backup-copies-screens.test.jsx` (the real module and Global Settings screens) and `backup-copies-polish.test.jsx` (copies with the progress count, the Undo wording and Delete all data).
- **Restore engine (`backupRestore`):** compute every change in memory → write ONE journal record → add photos / logos one at a time → add the localStorage text by PURE INSERTION (every existing byte stays) → verify → commit with ONE write that replaces the journal by the undo record. Both live in one key, `sparkcheck-restore-v1` (`{ journal, undo, problem }`: the record being written, the 14-day undo, and a note of what went wrong if a restore stopped). After any failure or a kill the phone's data is exactly what it was, or the restore is fully added, never a mix: `backupRecoverAtStart()` (in `src/main.jsx`, before the first render) finishes the recovery. The fills are journalled like the rest (`kind` "absent" for a key the restore creates, "text" with the original text for a key it changes), so a failed restore puts them back exactly. **Undo** is available for 14 days (`RESTORE_UNDO_DAYS`) and also takes out what the restore FILLED (`undo.filled`: per field / list / logo, what was there and what was written): a filled item is taken out only where it still holds exactly what the restore wrote, so something you changed since stays and the result says how many stayed; a key the restore created is removed once every list in it is back at the default. The Undo question (`backupUndoConfirmText`) and the "Restore undone" card (`backupUndoResultText`) leave out any count that is zero, with its words, and get the singular / plural and "was" / "were" right ("1 site and 2 calendar events", "2 sites, 3 History snapshots and 1 calendar event", "1 site was removed."); the card says "The business details, lists and settings it filled in were taken out." when both were taken out and names only the one that was otherwise; the restore result card, the summary and the Last restore line already leave zeros out. A database that exists but has no object store counts as nothing to clear.
- **The hang rule (approved; the numbers are in `eraseStepLimitMs`, `ERASE_RENDER_BUDGET_MS`, `ERASE_MAX_ATTEMPTS`):** each store step may take max(5 s, 18 ms per MB stored), capped at 30 s (500 MB is assumed when the size is unknown); the storage estimate itself is waited for 1 s (`ERASE_ESTIMATE_WAIT_MS`, an addition to the approved rule); the app waits 2 s for the erase before rendering (normally it is done in about a tenth of a second); past that it opens on **Global Settings only** (Backup & Data section, no Modules pill, the Business section held still, only the delete block, a "working" then a "retry" state); a step that runs out of time ends the attempt; after 3 attempts the marker is replaced by the note `sparkcheck-leftover-v1` and the app opens normally.
```bash
cd "C:\dev\SparkCheck\sparkcheck"
npm run dev           # starts Vite dev server at http://localhost:5173
```

```bash
npm run build         # outputs to dist/ — verify it builds before pushing

# Commit and push to dev branch (never push directly to main)

git push origin dev

git checkout main
git merge dev
git push origin main  # triggers GitHub Actions → auto-deploys to GitHub Pages
git checkout dev      # switch back to dev to continue working
```

## PWA / Service Worker

- `manifest.webmanifest` and `sw.js` are **generated at build time** by `vite-plugin-pwa` (configured in `vite.config.js`) — do not hand-author these files again. The plugin's `manifest:` option in `vite.config.js` is the source of truth for app name/icons/theme colors.
- Static assets the deployed site must serve (icons, etc.) belong in `public/` — Vite only copies that folder's contents into `dist/`. A file at the project root next to `index.html` is silently excluded from the build.
- Update flow: Workbox's precache manifest is content-hashed per build, so cache-first is safe for the app shell (a new build always has new filenames — nothing stale is ever referenced). `registerType: 'prompt'` means a downloaded update sits ready in the background; the user must tap "Refresh" in the `UpdateToast` banner (`src/main.jsx`) before it activates, via `skipWaiting()`/`clients.claim()` firing on that click. If you want new builds to activate silently and automatically instead (at the cost of possibly reloading someone mid-audit), change `registerType` to `'autoUpdate'` in `vite.config.js`.
- **History**: prior to 2026-09-22, `sw.js`/`manifest.json`/icons were hand-maintained files sitting at the project root — none of them were actually reaching `dist/` (no `public/` folder existed), so the deployed site had a 404'd manifest/service-worker/icons and *no offline support at all*, unnoticed for some time. Separately, the old `sw.js`'s service-worker *registration* call had been deleted from `index.html` during the original Vite migration and never restored, and its hand-written precached asset list (`./app.js`, `./react.js`) didn't match Vite's actual hashed output filenames. All of this was replaced by the `vite-plugin-pwa` setup described above, which generates the precache list from the real build output so it can't drift again.

## Encoding Safety (Windows / UTF-8)

`src/App.jsx` is a large UTF-8 file. On Windows, several shell tools corrupt it silently.

**Always use the `Edit` tool (`str_replace`) for edits to `src/App.jsx`.**

If `str_replace` cannot find a unique match and a file write is unavoidable, use Node.js — it handles UTF-8 correctly on Windows:
```js
node -e "const fs=require('fs'); let c=fs.readFileSync('src/App.jsx','utf8'); c=c.replace(/exact_old_text/,'new_text'); fs.writeFileSync('src/App.jsx',c,'utf8');"
```
Never use `cat >`, `sed -i`, heredoc (`<< 'EOF'`), or any shell redirect to write to `src/App.jsx`.
