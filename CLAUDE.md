## What This App Is

SparkCheck is a **Progressive Web App (PWA)** for electrical auditors and site electricians. It runs entirely in the browser with no backend — all data is stored in `localStorage`. It is deployed as a static site via **GitHub Actions → GitHub Pages** and can be installed on iOS/Android as a standalone app.

The app is built with **React + JSX**, bundled by **Vite**. Source lives in `src/App.jsx` (~11,800 lines). The entry point is `index.html` → `src/main.jsx` → `src/App.jsx`.

**Version:** v11 (shown in AppRoot footer)
**Brand colour:** `#e8731a` (SparkCheck orange)
**Light theme throughout:** background `#e8e6e2`, surface `#f7f6f3` (the earlier dark `#111`/`#161616` theme is gone)

## Architecture

### File Structure
```
sparkcheck/
├── index.html                  — Vite entry point (PWA meta, loading screen, splash)
├── src/
│   ├── main.jsx                — Mounts <AppRoot />, service-worker update-prompt toast
│   └── App.jsx                 — Entire application (~11,800 lines)
├── public/                     — Static files copied verbatim into dist/ root by Vite
│   ├── icon-192.png            — PWA icon
│   ├── icon-512.png            — PWA icon
│   └── icon.svg                — SVG icon
├── dist/                       — Build output (git-ignored, generated by `npm run build`)
├── .github/
│   └── workflows/
│       └── deploy.yml          — GitHub Actions: build → deploy to GitHub Pages
├── vite.config.js              — Vite config, incl. vite-plugin-pwa (generates manifest + sw.js)
├── package.json                — Dependencies: react, react-dom, xlsx, exceljs, vite, vite-plugin-pwa
└── CLAUDE.md                   — This file
```

**Note:** `manifest.json` and `sw.js` are no longer hand-authored files in the repo — `vite-plugin-pwa` generates `manifest.webmanifest` and `sw.js` into `dist/` at build time (see PWA / Service Worker section below). Any static file the deployed site needs to serve (icons, etc.) must live under `public/` — Vite only copies that folder into `dist/`; a file sitting at the project root next to `index.html` is **not** included in the build output (this bit the project once already — see git history around 2026-09-22).

### Build Pipeline
- **Dev server:** `npm run dev` — Vite HMR at `http://localhost:5173`
- **Production build:** `npm run build` — outputs to `dist/`
- **Deploy:** Push to `main` → GitHub Actions runs build → deploys `dist/` to GitHub Pages automatically
- **No manual file editing of dist/** — always edit `src/App.jsx`, then build

### XLSX Library
The `xlsx` (SheetJS) package is imported as:
```js
import * as XLSX_LIB from 'xlsx';
const XLSX = XLSX_LIB; // module-level alias — all bare XLSX. calls resolve here
```
Do not change this pattern. There are known security vulnerabilities in the xlsx package — do **not** run `npm audit fix --force` as it will break things.

### State & Storage
- All data lives in `localStorage` under versioned keys (e.g. `rcd-projects-v6`, `rcd-results-v6`)
- Each module has its own storage keys to avoid collisions
- Async `load(key, fallback)` and `save(key, val)` helpers wrap localStorage with error handling
- Storage-full warning banner shown to user if save fails

**Date maths rule (app-wide):** ISO `YYYY-MM-DD` strings parse as UTC midnight, so month/year additions must use `setUTCMonth`/`setUTCFullYear` (`addMonthsISO`, `addYearsISO`, `addTATMonths`). ## Excel Import/Export

Each module supports importing project structure from Excel and exporting results to styled Excel reports.

**Import** (`parseExcelToProject`): Handles two template formats:

- New 3-column: `Area | Panel | Circuit [| CB Type | Amp Rating]`

**Export**: Styled XLSX using the `xlsx` (SheetJS) package. Colours match the on-screen defects register. Priority rows colour-coded: Urgent = dark maroon, High = light red, Medium = yellow, Low = light green.

## Design System / Interaction Standards

### Standard Delete Pattern — applies to ALL modules, ALL destructive actions

All destructive actions use a **two-step inline confirmation** via the shared `DeleteButton` component.
**Never use `window.confirm()`, modals, browser dialogs, or any other confirmation pattern.**

#### Component signature
Defined once in `App.jsx` — after the shared utility functions, before the first module function.

```js
// Module-level variable — ensures only one DeleteButton is in confirm state at a time
let activeDeleteSetter = null;

function DeleteButton({ onDelete, label = 'Delete?' }) {
  const [confirming, setConfirming] = React.useState(false);

  const open = () => {
    if (activeDeleteSetter && activeDeleteSetter !== setConfirming) {
      activeDeleteSetter(false); // close any other open instance
    }
    activeDeleteSetter = setConfirming;
    setConfirming(true);
  };

  const cancel = () => {
    activeDeleteSetter = null;
    setConfirming(false);
  };

  const confirm = () => {
    activeDeleteSetter = null;
    setConfirming(false);
    onDelete();
  };

  if (!confirming) {
    return React.createElement('button', {
      onClick: open,
      style: {
        border: '1px solid rgba(239,68,68,0.35)',
        color: 'rgba(239,68,68,0.7)',
        background: 'transparent',
        borderRadius: '6px',
        padding: '4px 8px',
        cursor: 'pointer',
        fontSize: '13px',
        lineHeight: 1,
      }
    }, '🗑');
  }

  return React.createElement('div', {
    style: { display: 'flex', alignItems: 'center', gap: '8px' }
  },
    React.createElement('span', {
      style: { color: '#f87171', fontSize: '13px' }
    }, label),
    React.createElement('button', {
      onClick: confirm,
      style: {
        background: 'rgba(239,68,68,0.12)',
        border: '1px solid rgba(239,68,68,0.5)',
        color: '#f87171',
        borderRadius: '999px',
        padding: '4px 14px',
        fontSize: '13px',
        cursor: 'pointer',
        display: 'flex',
        alignItems: 'center',
        gap: '6px',
      }
    }, '🗑 Delete'),
    React.createElement('button', {
      onClick: cancel,
      style: {
        background: 'rgba(255,255,255,0.06)',
        border: '1px solid rgba(255,255,255,0.12)',
        color: '#aaa',
        borderRadius: '999px',
        padding: '4px 14px',
        fontSize: '13px',
        cursor: 'pointer',
      }
    }, 'Keep')
  );
}
```

#### Usage
```js
// Inside a map() — always close over the item id
React.createElement(DeleteButton, { onDelete: () => deleteItem(item.id) })

// Custom label
React.createElement(DeleteButton, { onDelete: () => removeArea(area.id), label: 'Remove area?' })
```

#### Behaviour rules
- **Idle state:** small 🗑 trash icon button, right-aligned, low emphasis, subtle red border
- **Confirming state:** same row expands to show `Delete?  [🗑 Delete]  [Keep]`
- **Keep:** returns to idle, no action taken
- **Delete:** calls `onDelete()` immediately, no further prompt
- **Only one open at a time** — opening any `DeleteButton` auto-closes all others via `activeDeleteSetter`
- **No layout shift** — row/card dimensions must not jump between idle and confirming states
- **No modals, no `window.confirm()`** — confirmation always happens inline in the row

#### What to remove when replacing old patterns
Remove all of the following when converting a delete action to `DeleteButton`:
- Any `window.confirm(...)` call
- Any home-grown confirm state variables: `deleteConfirm`, `confirmDelete`, `confirmId`, `showConfirm`, `pendingDelete`, `deletingId`, `deleteId` or similar
- Any inline ternary "Are you sure?" / confirmation UI rows
- Any modal or dialog that exists solely to confirm a delete

### Other shared standards (design-consistency batch)

- **Reset buttons** ("Reset" / "Reset to defaults" on any Dropdowns list) must go through the shared `ConfirmReset` wrapper — resetting silently discards customised options. **Dropdown option deletes** use `DeleteButton` with `compact: true`. `ConfirmReset`, `DeleteButton` and the Calendar event card all share `activeDeleteSetter`, so only one prompt is ever open. Covered by `src/reset-confirm.test.jsx` and `src/calendar-delete.test.jsx`.
- **Fail-only panel** ("⚠ FAIL — DEFECT DETAILS"): same red panel in every module; label `RECTIFIED / SCHEDULED ACTION`; Defect ID placeholder `e.g. 74`; the panel sits **before** the notes/comments box; Rectified and Responsibility use the editable dropdown fed by the module's customisable lists (TAT has `tat-dropdowns-v1`); defect data is **retained** when an item leaves FAIL (never cleared on save). The ★ default (first list option) is *stored* when an item becomes FAIL (`failFill` / `useFailDefaults`), not just displayed. **ELT now uses this same panel** (2026-09-26 — the old FAILURE REASON / ACTION TAKEN panel and `eltExportNotes` are gone; ELT's Dropdowns tab has Type + Responsibility + Rectified). Pre-standard ELT records are reconciled at READ time by `eltNormaliseRes` (only for FAIL records: old Action Taken -> `rectified`, old Failure Reason folded into the front of Notes as "Failure reason: X.", old keys dropped on the next save; passing / untested records keep the old fields hidden), and `upgradeEltDropdowns` retires the old lists (a customised Action Taken list carries over as Rectified). **Every export always carries its defect column headings even with zero fails** (static arrays; gating only blanks values) — `src/export-zero-fail.test.js` covers all eight modules. Thermo's MONITOR result has its own amber "⚠ MONITOR — DETAILS" panel and is not treated as a failure.
- **Save model — LIVE AUTO-SAVE everywhere (one standard, 2026-09-25)**: on every test-result item page (RCD, IEL, TAT, Thermo photo ledger, SWB, IRT, ELT, Welder) each change is written to storage immediately — no draft, no Save button, no "unsaved changes" prompt; Back just leaves. ELT, SWB and IRT were converted from Save-button drafts (`src/live-save.test.jsx`). IRT keeps `status` as `"untested"` (= auto-detect from readings) until the user overrides it, so a save never freezes a derived FAIL. Manage / Calendar forms keep their explicit Save buttons (record-editing forms, not test results); Thermo's "Add Photo" is an add-entry form that already commits per entry. Full rules and the measured write cost: NEW_MODULE_GUIDE.md §4 "SAVE MODEL".
- **Report tab**: build it from `ReportStatTiles`, `ReportFailedItems` ("Failed Items": title, path, Defect ID, notes, → Responsibility, Rectified/Scheduled Action) and `ReportNoDefects` ("✓ No defects recorded"). Failed Items lists only items whose status is FAIL (retained defect data on a PASS item must never list it). No Export button on the Report tab — export lives in History. **Exports** only write defect details (Defect ID, Responsibility, Priority, Rectified / Scheduled, Risk) for FAIL rows (Thermo: FAIL and MONITOR) — new exports must read items through `defectGate` / `defectGateByStatus`, because that data is retained on the item after it leaves FAIL (`src/export-defect-gating.test.js`). RCD push and injection exports/report rows both carry the defect columns. ELT shows four tiles (Total, Pass, Fail, Untested) — it has no N/A result.
- **Print-friendly exports (2026-09-26)** — RCD (push + injection), IEL, TAT, Thermo, IRT and ELT are split into a NARROW main results table (`#`, identifiers, dates, result, key values, **Notes** — compliance dates and pass-row notes never move) plus a separate **`Defects` sheet** (FAIL rows only: Defect ID, Priority, Rectified / Scheduled, Date Rectified / Scheduled, Responsibility, Notes) linked by the `#` column, which is a plain row number assigned at export (Defect ID is optional / not unique, so it cannot be the key). The Defects sheet ALWAYS exists with its headings, plus a "No defects recorded" line when empty. IRT has THREE sheets: `Register` (short + narrow — the client-PDF sheet), `Readings` (all 10 readings, units stated once in the header block) and `Defects`; the Register stays the FIRST sheet because every importer reads sheet 1 by heading keywords. RCD's old Summary "Failed Circuits" list is replaced by `Defects` (a >300 ms injection result now counts as a defect there too). Builders: **`xjSplit` / `xjSheet` (ExcelJS)** — ALL eight modules' exports are now ExcelJS (converted RCD / IEL / TAT / Thermo / IRT in five stages, 2026-09-26; SheetJS silently drops every cell style and all page setup, so it is now used ONLY for reading imports and the blank import templates). Look and feel is the ELT / SWB one: plain header block (rows 1-4 no fill / border), wrapped + centred heading row (44pt), thin borders on every data cell, white / light-grey zebra rows, Pass green / Fail red (bold) / N/A grey / MONITOR amber (`xjResultStyle`, SWB_XC palette), colour-coded Priority on the Defects sheet. **Page setup is native** in the file (`xjPageSetup`): A4, landscape (RCD Summary portrait), fit to 1 page wide, 0.25" side margins, heading row 5 repeated, "Page x of y" footer. **Every date column is forced to >= `XJ_DATE_W` (13)**: dates are `dd/mm/yyyy` TEXT in wrapping cells and Excel / Sheets break a tight one at the "/" (headings `Date…`, `Test Date…`, `Next Test…` — always format with `fmtDate`; TAT's Next Test Due used to be ISO). The exports are `async`. Tests: `export-print-layout.test.js` (values, `#` cross-reference, page setup, re-import), `export-styles.test.js` (borders / colours / zebra / date widths, IRT three-way). To eyeball the layout in Excel / Sheets: `GEN_OUT=./sample-exports npx vitest run src/sample-exports.test.js` writes 60-row samples of every affected module.
- **TAT Electrical Test (2026-09-26)** — each TAT item has a second check next to the Visual Inspection tick box: `electricalCheck` = `""` (not recorded) / `"pass"` / `"fail"`, the result shown on the test-and-tag machine (PASS / FAIL buttons; re-tap clears). The overall result stays MANUAL (PASS / FAIL / N/A / UNTESTED): **PASS is only allowed when Visual is ticked AND Electrical passed** (`tatCanPass`), and **Electrical FAIL sets the overall result to FAIL** (stamps the tested date; the defect panel + ★ defaults follow as for any FAIL). Clearing a passed Electrical drops the PASS it justified to UNTESTED (`tatElectricalPatch`); a legacy PASS (nothing recorded) is never touched. The field is ADDITIVE and OPTIONAL: `tatGetItem` supplies `""` at read time (a copy — storage is never rewritten by a read), so there was no storage-key bump and legacy records / History snapshots load unchanged (`src/tat-electrical.test.jsx`, incl. a seeded property test). Also: `○ / ✓ / ✕ Electrical` chips on the item list and History, an `Electrical test: FAIL` line in the Report's Failed Items, and an `Electrical Test` export column after Visual Inspection (Fail red, Pass plain). The importer stays structure-only.
- **ELT Excel import** (`parseELTExcel`, Manual / Import toggle on the ELT site list): accepts an ELT export or the blank template (`ELT_COLUMNS`, 20 headings; older 14/15-column exports still import, because only the six identifying headings Location / Asset Location / Asset ID / Type / Maintained / Fitting are read). **Structure only** — it reads Location, Asset Location (required), Asset ID, Type, Maintained, Fitting; results, dates and notes are ignored. The header row must match >= 3 ELT headings *exactly* (never a fuzzy "contains" match on title text — the SWB re-import bug) and include Asset Location. Unknown Type values import as "Other" + the text. The site name is taken by stripping the " — Emergency Lighting Test" suffix (not by splitting on hyphens), and the "SparkCheck" / template placeholders are ignored. Tests: `src/elt-import.test.js`, `src/elt-import-ui.test.jsx`.
- **Welder Excel import** (`parseWelderExcel`, Manual / Import toggle on the Welder site list, rose `#be185d` on `#fce7f3`): accepts a Welder export or the blank template (`Welder_Import_Template.xlsx`, same 13 `WELDER_COLUMNS`). **Structure only** — reads the Register sheet's Location, Asset ID, Welder (Machine), Serial Number; dates, Pass / Fail, defect columns, notes and every per-welder checklist result are ignored. Header row = >= 3 of those 4 headings matching exactly, and `Welder (Machine)` must be present (a row may leave it blank if it has an Asset ID; rows with neither are skipped). Unlike ELT, the Register lists ALL welders (tested or not), so a re-import recovers the full list. **Brand / Model**: the Register only has the joined "Welder (Machine)" text (unsplittable — "Lincoln Electric" + model), so exact Brand / Model come from the matching per-welder sheet's `Brand:` / `Model:` cells, trusted only when that sheet verifiably belongs to the row (same position, Asset ID and Serial agree, Brand + Model rejoin to the Register text). Otherwise (template, hand-made file, mis-ordered sheets) the whole text goes in Brand and the preview says so. Site name: strip ` — Welder Test` **or the pre-rename ` — Welder (VRD) Test`** (real historical exports), never split on hyphens. An ELT file gets a friendly "looks like an ELT file" message. Tests: `src/welder-import.test.js` (unit + real `exportWelderExcel` round trip), `src/welder-import-ui.test.jsx` (toggle, preview, and the full UI export -> fresh-app import pipeline).
- **Area grouping (ELT + Welder) — Site → Area → Assets, exactly two levels** (added 2026-09-25; this REVERSED the earlier deliberate "flat asset list" exception). Shape: `site.areas:[{id,name,assets:[…]}]`; an asset no longer stores `location` — its area's name is the Location (`areaAssets(site)` yields the flat list in area order, annotated with `location` + `areaId`; every summary, report, register and export reads through it, which is what makes exports come out grouped by area). ELT's `assetLocation` ("SE Door") stays on the asset. Results stay keyed `results[siteId][assetId]` (NOT nested by area), so moving an asset between areas needs no results migration. **Storage**: `elt-projects-v2` / `elt-history-v2` / `welder-projects-v2` / `welder-history-v2` (snapshots carry `areas`); results, meta and dropdowns stay `-v1` (unchanged shape). **Migration** (`loadVersioned` + `migrateProjectToAreas` / `migrateHistoryToAreas`, pure, tested in `src/area-migration.test.js`): the v2 key is read first; only if absent is the v1 key read and converted, and **the v1 key is never written or deleted** (permanent backup). Each asset's Location becomes an area — grouped case- and whitespace-insensitively, blank Location = the site name, first-appearance order, first-seen spelling, deterministic ids — so many assets sharing a Location land in ONE area. Area names are unique per site (add/rename to an existing name is refused). Manage uses the shared `AreaManager` (IRT-style collapsible area cards, inline rename, `DeleteButton`, add-area box; an Area select in the asset edit form moves an asset); Audit is one grouped list (`AreaAuditGroups`); Report has an AREA SUMMARY (`AreaSummaryRows`); History snapshots show area headers. **Deleting an asset or area also deletes its results and photos** (`removeAssetResults`) — a deliberate improvement over RCD/IEL/TAT/Thermo/SWB/IRT, which orphan results and photos on delete (candidate for a future backport; the older modules were intentionally not touched). Import: the Location column becomes the area (blank -> the site name as currently typed in the preview); the preview shows "N fittings in M areas". Export: column A "Location" is the area name, rows ordered by area then original order within the area, no separator rows (so re-import round-trips); per-welder sheets and the ELT Photos sheet follow the same order. Tests: `src/area-migration.test.js`, `src/area-views.test.jsx`, `src/area-import.test.jsx`. Each module keeps its own subtitle ("RCD AUDIT REPORT", …).

## PWA / Service Worker

- `manifest.webmanifest` and `sw.js` are **generated at build time** by `vite-plugin-pwa` (configured in `vite.config.js`) — do not hand-author these files again. The plugin's `manifest:` option in `vite.config.js` is the source of truth for app name/icons/theme colors.
- Static assets the deployed site must serve (icons, etc.) belong in `public/` — Vite only copies that folder's contents into `dist/`. A file at the project root next to `index.html` is silently excluded from the build.
- Update flow: Workbox's precache manifest is content-hashed per build, so cache-first is safe for the app shell (a new build always has new filenames — nothing stale is ever referenced). `registerType: 'prompt'` means a downloaded update sits ready in the background; the user must tap "Refresh" in the `UpdateToast` banner (`src/main.jsx`) before it activates, via `skipWaiting()`/`clients.claim()` firing on that click. If you want new builds to activate silently and automatically instead (at the cost of possibly reloading someone mid-audit), change `registerType` to `'autoUpdate'` in `vite.config.js`.
- **History**: prior to 2026-09-22, `sw.js`/`manifest.json`/icons were hand-maintained files sitting at the project root — none of them were actually reaching `dist/` (no `public/` folder existed), so the deployed site had a 404'd manifest/service-worker/icons and *no offline support at all*, unnoticed for some time. Separately, the old `sw.js`'s service-worker *registration* call had been deleted from `index.html` during the original Vite migration and never restored, and its hand-written precached asset list (`./app.js`, `./react.js`) didn't match Vite's actual hashed output filenames. All of this was replaced by the `vite-plugin-pwa` setup described above, which generates the precache list from the real build output so it can't drift again.

## Encoding Safety (Windows / UTF-8)

`src/App.jsx` is a large UTF-8 file. On Windows, several shell tools corrupt it silently.

**Always use the `Edit` tool (`str_replace`) for edits to `src/App.jsx`.**

If `str_replace` cannot find a unique match and a file write is unavoidable, use Node.js — it handles UTF-8 correctly on Windows:
```js
node -e "const fs=require('fs'); let c=fs.readFileSync('src/App.jsx','utf8'); c=c.replace(/exact_old_text/,'new_text'); fs.writeFileSync('src/App.jsx',c,'utf8');"
```
Never use `cat >`, `sed -i`, heredoc (`<< 'EOF'`), or any shell redirect to write to `src/App.jsx`.
