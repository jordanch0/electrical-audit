## CLAUDE.md · Project Intelligence File

## What This App Is

SparkCheck is a **Progressive Web App (PWA)** for electrical auditors and site electricians. It runs entirely in the browser with no backend — all data is stored in `localStorage`. It is deployed as a static site via **GitHub Actions → GitHub Pages** and can be installed on iOS/Android as a standalone app.

The app is built with **React + JSX**, bundled by **Vite**. Source lives in `src/App.jsx` (~11,800 lines). The entry point is `index.html` → `src/main.jsx` → `src/App.jsx`.

**Version:** v11 (shown in AppRoot footer)
**Brand colour:** `#e8731a` (SparkCheck orange)
**Light theme throughout:** background `#e8e6e2`, surface `#f7f6f3` (the earlier dark `#111`/`#161616` theme is gone)

**Note:** `manifest.json` and `sw.js` are no longer hand-authored files in the repo — `vite-plugin-pwa` generates `manifest.webmanifest` and `sw.js` into `dist/` at build time (see PWA / Service Worker section below). Any static file the deployed site needs to serve (icons, etc.) must live under `public/` — Vite only copies that folder into `dist/`; a file sitting at the project root next to `index.html` is **not** included in the build output (this bit the project once already — see git history around 2026-09-22).

### Build Pipeline
- **Dev server:** `npm run dev` — Vite HMR at `http://localhost:5173`
- **Production build:** `npm run build` — outputs to `dist/`
- **Deploy:** Push to `main` → GitHub Actions runs build → deploys `dist/` to GitHub Pages automatically
- **No manual file editing of dist/** — always edit `src/App.jsx`, then build

### XLSX Library
The `xlsx` (SheetJS) package is imported as:
```js
import * as XLSX_LIB from 'xlsx';
const XLSX = XLSX_LIB; // module-level alias — all bare XLSX. calls resolve here
```
Do not change this pattern. There are known security vulnerabilities in the xlsx package — do **not** run `npm audit fix --force` as it will break things.

### State & Storage
- All data lives in `localStorage` under versioned keys (e.g. `rcd-projects-v6`, `rcd-results-v6`)
- Each module has its own storage keys to avoid collisions
- Async `load(key, fallback)` and `save(key, val)` helpers wrap localStorage with error handling
- Storage-full warning banner shown to user if save fails

## Module Map

`AppRoot` is the home screen (near end of `App.jsx`). It renders one card per audit module (9 in a 2-column grid: RCD, IEL, TAT, Thermo, SWB, IRT, ELT, Welder, General Site Defects) and routes to each via a `module` state string. **Calendar is not a grid card** — it is opened from a pill (`data-testid="calendar-pill"`, aria-label "Open Test Calendar") in a dedicated bar below the module grid, alongside the Global Settings pill (`data-testid="settings-pill"`). The header block pads with `env(safe-area-inset-top)` (never a fixed pixel offset) so it clears the iPhone notch / Dynamic Island. Each module is self-contained with its own state, views, and storage keys.

**Bottom bars: layout history, and the Facebook-style overlay restyle (2026-09-29 -> 2026-09-30)**:
1. **Non-scrolling reserved layout (kept from the 2026-09-30 re-fix)**: the scrollable module grid and the Home-screen bottom bar are SEPARATE flex children of the home screen's outer column — the grid in a `flex:1, overflowY:"scroll"` region, the bar in a non-scrolling row below it. **This replaced an earlier `position:fixed` pill design** that floated two pills OVER the scrollable grid: whatever content happened to be scrolled to that fixed screen position — including the last module card — could end up directly behind them (a first-attempt trailing spacer only protected the one scroll position where it lined up with the still-floating pills, and was confirmed still broken). A real reserved region is the only fix that holds at every scroll position and at any module count (row-count-invariant by construction).
2. **Facebook-style overlay restyle (2026-09-30, replaces the visual skin of both bars — the layout above is unchanged)**: both the Home bar and every module's in-module bottom nav bar (`bottomNav` in each module's own style object — `S`/RCD, `SI`/IEL, `CAL_STYLE`/Calendar, `ST`/TAT, `STH`/Thermo, `swbStyles()`/SWB+ELT+Welder+GSD, `irtStyles()`/IRT) now use an **overlay treatment matching Facebook's bottom nav**: background is the page's own `#e8e6e2` (not a contrasting `#f7f6f3` filled strip), the only divider is a single `borderTop: 1px solid #e4e4e7`, and the old `boxShadow: "0 200px 0 200px #f7f6f3"` fill-hack is gone (it existed only to visually extend that now-removed contrasting strip). Height is shorter/more compact: `NavBtn` (and its 3 module-local copies — `IELNavBtn`, `TATNavBtn`, `SWBNavBtn`; **any new one must match**) dropped from `minHeight:50, padding:"10px 0 6px"` to `minHeight:42, padding:"6px 0 4px"`, same icons/labels/order. The Home bar's Calendar/Settings buttons changed from bordered, shadowed, pill-shaped buttons to plain icon+label buttons in NavBtn's own shape, laid out as a flex row (`display:"flex"`, each button `flex:1`) instead of a "one centred, one pinned right" 3-column grid — Calendar still comes before Settings, left to right.
**(2026-10-01 SUPERSEDES points 1-3 below for the current design: both bars are now ONE floating pill overlaid on the content — see "Bottom nav (floating pill)" under Coding Conventions. The in-flow / `--kb-inset` / `borderTop` / minHeight-42 details below are history.)**
3. **Safe-area bottom padding**: every `bottomNav` (and the Home bar) pads with `env(safe-area-inset-bottom, 0px)`, not a hardcoded `34px` — the flat 34px assumption didn't match the real home-indicator inset in standalone mode on the device it was tested on. **A separate, pre-existing bug also had to be fixed for this to actually reach the true bottom edge**: `index.html`'s keyboard-inset tracking (`--kb-inset`, applied only as the nav bar's own `margin-bottom`, so the keyboard lifts just the tab bar) computed the inset as the raw, instantaneous `window.innerHeight - visualViewport.height`, which in an installed standalone session can sit at a standing non-zero value (roughly the safe-area-inset-bottom amount) even with no keyboard open — read literally, that stale diff became a permanent extra margin below the nav, showing as a visible gap of page background beneath it. Fixed by tracking the LOWEST diff ever observed as the resting ("no keyboard") baseline and reporting only the amount above it (self-corrects downward too, e.g. after rotation).
Reference screenshots for the Facebook restyle: `reference-images/facebook-bottom-nav/` (gitignored — real device photos, not committed).
Tests: `src/safe-area-layout.test.jsx` (nav/bar background, border, no-box-shadow, and NavBtn height are verified by reading the source, since jsdom's CSSOM doesn't understand `env()` and silently drops it from a read-back style; the Home bar's non-`position:fixed`/non-nested-in-scroll-region/flex-row layout is verified via DOM structure checks; the keyboard-inset baseline logic is verified by a source-text check plus a faithful re-implementation of the algorithm, since `index.html`'s script is deliberately inline, non-modularised JS that must run before the React bundle loads).

## Coding Conventions

- **React.createElement** — all components use `React.createElement(...)` (no JSX syntax in source — Vite handles the transform but the code pre-dates JSX migration and was not converted)
- **Single file** — all components remain in `src/App.jsx`; do not split into separate files unless explicitly asked
- **Functional components only** — React hooks (`useState`, `useEffect`, `useCallback`, `useRef`, `useMemo`)
- **Inline styles everywhere** — no CSS classes, no stylesheets. All styling via `style={{...}}` objects
- **Light theme constants**: bg `#e8e6e2`, surface `#f7f6f3`, border `#e4e4e7`, text `#18181b`, muted `#52525b`
- **Bottom nav (floating pill, 2026-10-01)**: every module AND the Home screen use ONE floating pill, `NAV_PILL_STYLE` (`NAV_PILL_STYLE_NARROW` on Home: 2 tabs, max 240px, centred) — `position:absolute` over the content, 14px from each side, `borderRadius:999`, translucent white + blur, `0 4px 16px rgba(0,0,0,0.12)` shadow. **Size/position (re-measured against Facebook's bar, 2026-10-01): pill 52px tall (`NAV_PILL_H`: 44px buttons + 3px padding + 1px border); bottom offset `NAV_BOTTOM = max(8px, env(safe-area-inset-bottom) - 14px)` = 20px on a home-indicator iPhone (the pill DIPS into the safe area like Facebook's), 8px where there is no inset; `NAV_CLEARANCE = NAV_PILL_H + NAV_BOTTOM + 16px` (= 88px on such an iPhone).** `NAV_BOTTOM` is the single bottom number — the pill and `NAV_CLEARANCE` both use it; never hard-code a bottom offset. It relies on `viewport-fit=cover` in index.html's viewport meta (without it the inset is 0 and the pill can't dip). ONE button, `NavBtn` (`IELNavBtn`/`TATNavBtn`/`SWBNavBtn`/`ThermoNavBtn`/`IRTNavBtn` are aliases — never write another): the active tab is a `#fdeadb` rounded highlight with `#a3530f` icon + label, inactive `#3f3f46`, 11px labels, `NAV_BTN_H` 44px (tap target never lower). Every module's `bottomNav` is just `NAV_PILL_STYLE`.
- **SCROLLABLE SCREENS MUST USE `NAV_CLEARANCE` FOR BOTTOM PADDING — never a hard-coded number.** The pill floats OVER the scroll area, so any scroll container on a screen that shows the pill must end with `paddingBottom: NAV_CLEARANCE` (pill height + gap + safe-area inset + breathing room). This is what the 2026-09-29/30 overlay attempts got wrong twice (last card hidden behind the bar). The module `main` regions and the Home grid carry it; views rendered INSIDE `main` must not add their own (it would double up). New scroll area = use `NAV_CLEARANCE`. `src/safe-area-layout.test.jsx` scans the source and fails on a `main` region without it or a `paddingBottom: 80/100` literal.
- **iOS standalone short web view — why the pill once sat ~47pt too high (2026-10-01). Cause: `html, body { height: 100% }` alone.** On a real iPhone (installed, portrait) `window.innerHeight` was 879 on a 926pt screen: `100%` resolved 47pt short (the status-bar inset) and the WEB VIEW followed it — nothing below 879 is ever painted, so `#root`'s `bottom:0` and the pill (correctly 20px above it) sat 67pt above the real bottom with a blank strip underneath. Nothing in the app added the inset twice, the browser / iframe can't show it (inset 0), and sizing `#root` taller with JS does NOT work (the pill's lower half is clipped at 879). Found with a live-experiment panel on the phone: only `html/body height:100vh` moved `innerHeight` 879 -> 926 (re-adding the viewport meta, `overflow:visible`, `scrollTo`, `body:fixed` did nothing). **Fix: `index.html` declares `height:100%` and then `height:100vh` on `html, body`** (`100vh` = 926 there). Rules: never remove that `100vh` line; never "fix" iOS viewport height with JS reading `screen.height` / `innerHeight`; and judge pill / bottom-edge positions on a real device (a desktop browser's inset is 0). Tests: `src/safe-area-layout.test.jsx` (the 100%-then-100vh order, and no `screen.height` hack).
- **The pill must NEVER depend on `--kb-inset`, and it HIDES while the keyboard is open (2026-10-01).** `--kb-inset` (a margin-bottom on the nav) lifted the pill with the iOS keyboard and was left stale when a nav tap closed the keyboard without a final viewport event (pill stranded mid-screen). It is gone — nothing in `index.html` or `src/` sets or reads it. Instead `index.html`'s inline script derives `html.kb-open` from `document.activeElement` (a text input / textarea / select / contenteditable) on focusin / focusout / blur / visualViewport resize+scroll / pagehide, and `html.kb-open #root nav` is `opacity:0; pointer-events:none` (0.15s fade). A nav-button press blurs the field first. Never position anything off the keyboard height; it can't be read reliably on iOS.
- **Section dividers**: `// ─────────────────────────────────────────────────────────────────────────`
- **Australian locale**: dates DD/MM/YYYY, currency $AUD implied, standards references to AS/NZS
- **Default export**: `App.jsx` ends with `export default AppRoot`

## Design System / Interaction Standards

### Standard Delete Pattern — applies to ALL modules, ALL destructive actions

All destructive actions use a **two-step inline confirmation** via the shared `DeleteButton` component.
**Never use `window.confirm()`, modals, browser dialogs, or any other confirmation pattern.**

#### Component signature
Defined once in `App.jsx` — after the shared utility functions, before the first module function.

```js
// Module-level variable — ensures only one DeleteButton is in confirm state at a time
let activeDeleteSetter = null;

function DeleteButton({ onDelete, label = 'Delete?' }) {
  const [confirming, setConfirming] = React.useState(false);

  const open = () => {
    if (activeDeleteSetter && activeDeleteSetter !== setConfirming) {
      activeDeleteSetter(false); // close any other open instance
    }
    activeDeleteSetter = setConfirming;
    setConfirming(true);
  };

  const cancel = () => {
    activeDeleteSetter = null;
    setConfirming(false);
  };

  const confirm = () => {
    activeDeleteSetter = null;
    setConfirming(false);
    onDelete();
  };

  if (!confirming) {
    return React.createElement('button', {
      onClick: open,
      style: {
        border: '1px solid rgba(239,68,68,0.35)',
        color: 'rgba(239,68,68,0.7)',
        background: 'transparent',
        borderRadius: '6px',
        padding: '4px 8px',
        cursor: 'pointer',
        fontSize: '13px',
        lineHeight: 1,
      }
    }, '🗑');
  }

  return React.createElement('div', {
    style: { display: 'flex', alignItems: 'center', gap: '8px' }
  },
    React.createElement('span', {
      style: { color: '#f87171', fontSize: '13px' }
    }, label),
    React.createElement('button', {
      onClick: confirm,
      style: {
        background: 'rgba(239,68,68,0.12)',
        border: '1px solid rgba(239,68,68,0.5)',
        color: '#f87171',
        borderRadius: '999px',
        padding: '4px 14px',
        fontSize: '13px',
        cursor: 'pointer',
        display: 'flex',
        alignItems: 'center',
        gap: '6px',
      }
    }, '🗑 Delete'),
    React.createElement('button', {
      onClick: cancel,
      style: {
        background: 'rgba(255,255,255,0.06)',
        border: '1px solid rgba(255,255,255,0.12)',
        color: '#aaa',
        borderRadius: '999px',
        padding: '4px 14px',
        fontSize: '13px',
        cursor: 'pointer',
      }
    }, 'Keep')
  );
}
```

#### Usage
```js
// Inside a map() — always close over the item id
React.createElement(DeleteButton, { onDelete: () => deleteItem(item.id) })

// Custom label
React.createElement(DeleteButton, { onDelete: () => removeArea(area.id), label: 'Remove area?' })
```

#### Behaviour rules
- **Idle state:** small 🗑 trash icon button, right-aligned, low emphasis, subtle red border
- **Confirming state:** same row expands to show `Delete?  [🗑 Delete]  [Keep]`
- **Keep:** returns to idle, no action taken
- **Delete:** calls `onDelete()` immediately, no further prompt
- **Only one open at a time, and a click OUTSIDE collapses it** — both come from the shared `useCollapsible(open, close, ref)` hook (module-level `activeExpander`; a document-level `click` listener in the CAPTURE phase, deliberately not `pointerdown`, so a layout shift can never lose a tap). It is used by `DeleteButton`, `ConfirmReset`, `CompleteAuditBtn`, the Calendar event card's delete, the popover of all five editable dropdowns and GSD's area picker; anything new that expands must use it. Deliberately NOT collapsible: inline add / edit forms (they hold typed input) and accordions (navigation). This replaced the old `activeDeleteSetter`. Tests: `src/collapsible.test.jsx`
- **No layout shift** — row/card dimensions must not jump between idle and confirming states
- **No modals, no `window.confirm()`** — confirmation always happens inline in the row

#### What to remove when replacing old patterns
Remove all of the following when converting a delete action to `DeleteButton`:
- Any `window.confirm(...)` call
- Any home-grown confirm state variables: `deleteConfirm`, `confirmDelete`, `confirmId`, `showConfirm`, `pendingDelete`, `deletingId`, `deleteId` or similar
- Any inline ternary "Are you sure?" / confirmation UI rows
- Any modal or dialog that exists solely to confirm a delete

### Other shared standards (design-consistency batch)

- **Reset buttons** ("Reset" / "Reset to defaults" on any Dropdowns list) must go through the shared `ConfirmReset` wrapper — resetting silently discards customised options. **Dropdown option deletes** use `DeleteButton` with `compact: true`. `ConfirmReset`, `DeleteButton` and the Calendar event card all share `activeDeleteSetter`, so only one prompt is ever open. Covered by `src/reset-confirm.test.jsx` and `src/calendar-delete.test.jsx`.
- **Fail-only panel** ("⚠ FAIL — DEFECT DETAILS"): same red panel in every module; label `RECTIFIED / SCHEDULED ACTION`; Defect ID placeholder `e.g. 74`; the panel sits **before** the notes/comments box; Rectified and Responsibility use the editable dropdown fed by the module's customisable lists (TAT has `tat-dropdowns-v1`); defect data is **retained** when an item leaves FAIL (never cleared on save). The ★ default (first list option) is *stored* when an item becomes FAIL (`failFill` / `useFailDefaults`), not just displayed. **ELT now uses this same panel** (2026-09-26 — the old FAILURE REASON / ACTION TAKEN panel and `eltExportNotes` are gone; ELT's Dropdowns tab has Type + Responsibility + Rectified). Pre-standard ELT records are reconciled at READ time by `eltNormaliseRes` (only for FAIL records: old Action Taken -> `rectified`, old Failure Reason folded into the front of Notes as "Failure reason: X.", old keys dropped on the next save; passing / untested records keep the old fields hidden), and `upgradeEltDropdowns` retires the old lists (a customised Action Taken list carries over as Rectified). **Every export always carries its defect column headings even with zero fails** (static arrays; gating only blanks values) — `src/export-zero-fail.test.js` covers all eight modules. Thermo's MONITOR result has its own amber "⚠ MONITOR — DETAILS" panel and is not treated as a failure.
- **Save model — LIVE AUTO-SAVE everywhere (one standard, 2026-09-25)**: on every test-result item page (RCD, IEL, TAT, Thermo photo ledger, SWB, IRT, ELT, Welder) each change is written to storage immediately — no draft, no Save button, no "unsaved changes" prompt; Back just leaves. ELT, SWB and IRT were converted from Save-button drafts (`src/live-save.test.jsx`). IRT keeps `status` as `"untested"` (= auto-detect from readings) until the user overrides it, so a save never freezes a derived FAIL. Manage / Calendar forms keep their explicit Save buttons (record-editing forms, not test results); Thermo's "Add Photo" is an add-entry form that already commits per entry. Full rules and the measured write cost: NEW_MODULE_GUIDE.md §4 "SAVE MODEL".
- **Storage safety net (2026-09-29)**: `save()` still writes only to `localStorage` — ELT/Welder/SWB photos moved to IndexedDB in the photo-migration work, but that's a separate store with its own per-call error handling (`sitePhotoStore`/`gsdPhotoStore`), not what `save()` guards. ## PWA / Service Worker

- `manifest.webmanifest` and `sw.js` are **generated at build time** by `vite-plugin-pwa` (configured in `vite.config.js`) — do not hand-author these files again. The plugin's `manifest:` option in `vite.config.js` is the source of truth for app name/icons/theme colors.
- Static assets the deployed site must serve (icons, etc.) belong in `public/` — Vite only copies that folder's contents into `dist/`. A file at the project root next to `index.html` is silently excluded from the build.
- Update flow: Workbox's precache manifest is content-hashed per build, so cache-first is safe for the app shell (a new build always has new filenames — nothing stale is ever referenced). `registerType: 'prompt'` means a downloaded update sits ready in the background; the user must tap "Refresh" in the `UpdateToast` banner (`src/main.jsx`) before it activates, via `skipWaiting()`/`clients.claim()` firing on that click. If you want new builds to activate silently and automatically instead (at the cost of possibly reloading someone mid-audit), change `registerType` to `'autoUpdate'` in `vite.config.js`.
- **History**: prior to 2026-09-22, `sw.js`/`manifest.json`/icons were hand-maintained files sitting at the project root — none of them were actually reaching `dist/` (no `public/` folder existed), so the deployed site had a 404'd manifest/service-worker/icons and *no offline support at all*, unnoticed for some time. Separately, the old `sw.js`'s service-worker *registration* call had been deleted from `index.html` during the original Vite migration and never restored, and its hand-written precached asset list (`./app.js`, `./react.js`) didn't match Vite's actual hashed output filenames. All of this was replaced by the `vite-plugin-pwa` setup described above, which generates the precache list from the real build output so it can't drift again.

## Encoding Safety (Windows / UTF-8)

`src/App.jsx` is a large UTF-8 file. On Windows, several shell tools corrupt it silently.

**Always use the `Edit` tool (`str_replace`) for edits to `src/App.jsx`.**

If `str_replace` cannot find a unique match and a file write is unavoidable, use Node.js — it handles UTF-8 correctly on Windows:
```js
node -e "const fs=require('fs'); let c=fs.readFileSync('src/App.jsx','utf8'); c=c.replace(/exact_old_text/,'new_text'); fs.writeFileSync('src/App.jsx',c,'utf8');"
```
Never use `cat >`, `sed -i`, heredoc (`<< 'EOF'`), or any shell redirect to write to `src/App.jsx`.
